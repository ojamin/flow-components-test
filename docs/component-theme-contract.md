# Component Theme Contract

## Purpose

This contract locks the canonical package-component theming lane and records the implemented package foundation.
It is grounded in archived Task Master Task 1 (`.taskmaster/tasks/tasks_archive.json`), the PRD product principles (`docs/gpt-pro-visual-site-builder.prd:56-64`), the Vite+/Tailwind rules (`docs/gpt-pro-visual-site-builder.prd:105-112`), Preview/static-export parity (`docs/gpt-pro-visual-site-builder.prd:969-981`), package authoring boundaries (`packages/components/docs/authoring-guide.md:48-53`), component styling boundaries (`packages/components/docs/design-system-for-components.md:8-16`), renderer styling boundaries (`packages/components/docs/renderer-guide.md:38-46`), and package guardrails (`packages/components/AGENTS.md:3-7`).

The current Issue #51 Task 1 expands the package-owned component-theme foundation: schema and SDK role lists, built-in JSON themes, exact sage/sand/ink fixture coverage, structured shadcn alias normalization, shadcn `:root` / `.dark` CSS import parsing, docs, and generated package artifacts. Earlier foundation work introduced the canonical `theme.theme` component, host placement-tree inheritance resolver, scoped `--ct-*` style bridge, renderer `themeContext` seam, Preview/Builder/package-preview wiring, forbidden non-layout theme-input pruning, static-export parity proof, and representative chart/SVG renderer migrations. The no-legacy cleanup removed hidden/load-only `viz.theme` / `viz-theme` compatibility; old references are rejection targets only.

The no-legacy cleanup branch locks the replacement contract in `docs/no-legacy-component-theme-cleanup-contract.md` and supersedes compatibility-retention guidance for `viz.theme`, `viz-theme`, old viz payload normalization, old tone aliases, and renderer legacy bridges while preserving the canonical behavior defined here. Rows marked **Removed by no-legacy cleanup** below describe historical state or rejection targets, not retention instructions.

### Canonical component I/O IDs

`theme.theme` is the only canonical `component-theme` producer. It computes the selected built-in theme plus sparse `propertyOverrides` and exposes these exact output IDs:

| Output ID         | Type contract                                | Purpose                                                                                                                                    |
| ----------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `theme`           | `component-theme`                            | Serializable merged theme payload for `layout.main-page` and slot-owning layout `theme` inputs.                                            |
| `properties`      | JSON/object-compatible property map          | Final resolved `properties` map for inspection, transforms, and tests that need the role groups without re-parsing the full theme payload. |
| `availableThemes` | JSON-array-compatible built-in metadata list | Stable built-in theme metadata in `default`, `midnight`, `aurora`, `sunrise`, `civic-results`, `command-center` order.                     |

The layout input ID is exactly `theme` with type ID `component-theme` on `layout.main-page`, `layout.card`, `layout.section`, `layout.split`, `layout.tabs`, `layout.view-stack`, and `layout.repeater` only. `layout.stack` inherits host theme context for its muted empty-state copy but does not declare a `theme` input.

## `component-theme` payload vocabulary

`component-theme` is a serializable object:

```ts
type ComponentThemeV1 = {
  version: 1;
  id: string;
  displayName: string;
  description?: string;
  properties: {
    color: Record<ComponentThemeColorRole, string>;
    font: Record<ComponentThemeFontRole, string>;
    radius: Record<ComponentThemeRadiusRole, string>;
    spacing: Record<ComponentThemeSpacingRole, string>;
    shadow?: Record<ComponentThemeShadowRole, string>;
    motion: {
      durationFastMs: number;
      durationNormalMs: number;
      easing: string;
    };
  };
};
```

- `md`

- `none`
- `sm`
- `md`
- `lg`
- `xl`

Required motion roles:

- `durationFastMs`
- `durationNormalMs`
- `easing`

Built-in theme values are actual OKLCH, HSL-channel, font, radius, spacing,
motion, and shadow values in `packages/components/src/themes/*.json` only.
Runtime overrides from `theme.theme` may set the same role keys only.
Color values are non-empty strings; HSL channel values such as `40 60% 99%` are
valid import data and should remain data values rather than executable CSS.
Some expanded roles are optional at the schema boundary for legacy compatibility,
but the role lists, built-in themes, SDK labels, and CSS-variable slots define
the canonical inventory for new component-theme payloads.

Raw shadcn `:root` and `.dark` CSS variable blocks may be parsed as import
input. `:root` becomes the light override set and `.dark` becomes the dark
override set. The parser only accepts custom property declarations for supported
shadcn tokens; selectors other than `:root` and `.dark`, non-variable
declarations, unknown aliases, invalid values, and conflicting repeated aliases
return stable diagnostics with paths, supported keys or suggestions when
available, and recovery instructions. The raw CSS block is discarded after
normalization and must not be persisted in project JSON, component-theme
payloads, or static export archives.

### Merge and fallback semantics

Theme payload production and structural propagation are separate steps.

`theme.theme` computes its output payload by starting from the selected built-in theme JSON and then applying its `propertyOverrides` for the same role keys.

The host resolver then resolves each inherited property by structural containment:

1. Start at the placement's nearest containing `layout.main-page` or slot-owning layout with a connected `theme` input.
2. If that connected payload contains the requested property, use it.
3. If the property is missing, continue upward through containing layouts until a property value is found.
4. If no containing layout provides the property, use built-in theme ID `default`.

For nested layouts, the nearest connected theme wins per property, not wholesale for the whole theme object. Example: if an inner `layout.card` theme overrides only `color.accent`, descendants use that inner accent and continue falling back to outer layout/default values for every missing role.

Missing unconnected layout theme inputs inherit silently and are not diagnostics.

CSS custom-property slots are fixed as `--ct-{role-group}-{role-key}`. Role key names use kebab-case; camelCase role keys convert to kebab-case for the variable suffix. Required examples include `--ct-color-page-background`, `--ct-font-body`, `--ct-radius-md`, and `--ct-motion-duration-fast-ms`. Scoped DOM application uses `data-ct-scope` or the equivalent approved host bridge owned by the resolver/static-export implementation.

## Package-side inventory

Package renderers and renderer-owned support files must paint visible site surfaces through static `ct-*` Tailwind aliases, host-supplied `themeContext`, or package-safe SDK helpers such as `resolveThemeProperty(...)` / role utility helpers. `@flow-builder/components/component-ui` remains an allowed package-owned facade for shadcn-vue primitives, but renderer use of global-token primitives is file-scoped: each non-headless facade import needs a precise scanner exception proving the renderer applies component-theme-aware `ct-*` classes at the call site or otherwise keeps visible styling under the scoped `--ct-*` bridge. This does not globally ban app/preview chrome from host shadcn tokens; it blocks built-in package component renderer-authored surfaces from bypassing `data-ct-scope`.

The monorepo app-integration lint gate historically included `scripts/lint-ui/package-component-theme-tokens.mjs` through `scripts/lint-ui/index.mjs` / root `npm run lint:ui`.
Standalone package contributors should treat that paragraph and the host path inventory below as compatibility context, not package-local setup.
Package-local enforcement runs through `npm run policy:standalone` and `npm run check:standalone`.
The token gate scans production `packages/components/src/groups/**/*.{vue,ts}` files excluding tests, fixtures, docs, `ConfigPanel.vue`, `component.ts`, and `types.ts`; reports host/global utility tokens, host CSS variables including old `--chart-*`, and unapproved `component-ui` facade imports; and permits only documented file-scoped facade exceptions.
This is an enforcement gate, not a claim that Task 6.10 browser proof is complete.

## Enforcement and migration policy

### Block

- Color/font/theme definitions outside `packages/components/src/themes/*.json`, except role-name-only schema/index helpers under `packages/components/src/themes/`, `packages/components/src/sdk/theme.ts` helper logic, approved host scoped style bridge values derived from resolved Theme output, tests, and fixtures.
- `component-theme` producers outside `packages/components/src/groups/theme/theme/`; `viz.theme` must remain removed and must not be accepted as a producer or adapter.
- Non-layout component input ID `theme` typed as `component-theme` or `viz-theme`.
- New raw color/font config controls outside the canonical Theme component.
- Inline `style` attributes, Vue SFC `<style>` blocks, and ad hoc CSS files outside the root allowlist.
- Package imports of host app stores, router modules, pages, app-shell UI, Builder internals, or non-allowlisted runtime internals.

### Classify as compatibility or migration context

- **Removed by no-legacy cleanup:** hidden/load-only `viz-theme` compatibility in `viz.theme`, legacy schema parsing, and tests/fixtures that prove saved-project replay are rejection targets only. Non-layout production component definitions must not expose `acceptedTypeIds: ["viz-theme"]` authoring inputs.
- Host app chrome theme presets (`.theme-blue`, `.theme-rose`, `useThemePreset`) until Task 5/7 either scopes them as app chrome compatibility or migrates them to the canonical component-theme bridge.
- Allowlisted raw values in built-in theme JSON, approved CSS token/bridge files, the canonical Theme/SchemaForm helpers, tests, fixtures, and `packages/components/src/groups/viz/shared/component-theme-colors.ts`.

### Allow

- `packages/components/src/themes/*.json` built-in theme values.
- Theme schema/index helpers that define role names and validation but do not introduce extra theme values.
- `packages/components/src/sdk/theme.ts` role/variable constants and deterministic helper logic that operates on host-supplied resolved context.
- The approved host scoped CSS-variable bridge that emits only values from resolved Theme output or built-in theme JSON.
- Canvas/SVG/Three conversion helpers that convert resolved theme values into numeric/API formats without independent fallback colors.
- Tests and fixtures that intentionally prove no-legacy rejection/absence or enforcement behavior.
- Package preview/editor chrome token usage when classified separately from end-user renderer theming.
- `src/lib/style-tokens.ts` as the approved host semantic tone-token helper for app-chrome/status class sets.

Legacy saved raw values are no-legacy rejection targets once compatibility is removed. They must not silently normalize into `component-theme`/default behavior or remain ongoing authoring controls.
