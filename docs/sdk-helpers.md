# SDK helper inventory and contract

## Purpose

This is the package helper documentation page for component authors. Start here when you need reusable SDK helpers instead of reaching into another component folder, a group-local `shared/` folder, or parent-app code.
It records the current helper sections, the preferred root-versus-subpath import rules, and the migration checklist for future helper slices.
It is source evidence for the SDK helper standardization task graph; it documents accepted helper surfaces without implying caller migrations or enforcement work are complete.

## Authoring boundary references

- Component code should use only public package surfaces, package-local relative imports, Vue, Zod, and declared dependencies.
- Component folders must not import host app stores, router modules, pages, app-shell UI, builder internals, or non-allowlisted runtime internals.
- Config panels should use `@flow-builder/components/component-ui`; component helpers intended for broad reuse should be proposed for public SDK surfaces instead of being hidden in a single component or group folder.

## Author quick reference

Look for helpers in two places before adding a new utility:

- `@flow-builder/components/sdk` for definition-loader-safe types and pure helpers that are safe in manifests, definitions, transforms, config parsing, and other non-renderer paths.
- `@flow-builder/components/sdk/<section>` for browser-, renderer-, DOM-, sanitization-, or Three-backed helpers that should not be pulled into the root SDK barrel.

Use `@flow-builder/components/component-ui` for package config-panel UI and SchemaForm wrappers; it is a UI facade, not a general SDK helper bucket.

## Sectioned SDK helper contract

Shared helpers belong in public SDK surfaces when they are reusable across component groups, independent of host app stores/runtime internals, and safe for external component authors to depend on.
The approved sections are:

| Section           | Intended contents                                                                                                                                                                 | Import surface                                                                                                                                                                                                                                        |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser helpers   | Guarded access to the browser environment, clipboard, timers, animation frames, canvas factories, focus lookup, `matchMedia`, and device-pixel-ratio.                             | Lightweight guards may be root-safe; DOM/browser-global adapters should prefer `@flow-builder/components/sdk/browser`.                                                                                                                                |
| Rendering helpers | Renderer setup/teardown utilities, reduced-motion resolution, frame-loop helpers, generic cleanup scopes, and disposal helpers that do not assume host app ownership.             | Lightweight lifecycle contracts may be root-safe; browser-backed rendering helpers should use `@flow-builder/components/sdk/rendering`.                                                                                                               |
| Capabilities      | Environment/capability checks such as WebGL support, reduced-motion availability, and feature predicates that components can branch on.                                           | Root-safe only when dependency-light and browser-guarded; otherwise `@flow-builder/components/sdk/capabilities`. WebGL detection is canonical here and is also re-exported from `@flow-builder/components/sdk/three-d` for 3D author discoverability. |
| Three-d           | Author-facing Three.js scene, renderer sizing, disposal, orbit, picking, WebGL detection convenience exports, stale async setup guards, color/motion, and frame-loop entrypoints. | Subpath-only: `@flow-builder/components/sdk/three-d`. Do not expose Three-backed helpers through the root SDK barrel.                                                                                                                                 |
| Interactions      | Generic activation-key checks, roving arrow navigation, stable interactive keys, ARIA label helpers, and non-color-only interaction affordance helpers.                           | Root-safe only for tiny pure helpers; richer interaction helpers should use `@flow-builder/components/sdk/interactions`.                                                                                                                              |
| Data              | Path reads, structured data normalization, primitive coercion, data-type helpers, row-transform contracts/engine helpers, and chart/data adapters that are generic across groups. | Existing lightweight data helpers and definition-loader-safe row-transform contracts may remain root-safe; larger adapters should use `@flow-builder/components/sdk/data`.                                                                            |
| Config            | Config field parsing, params binding state, schema primitives, and definition-safe config helpers.                                                                                | Root SDK for definition/config helpers or `@flow-builder/components/sdk/config` when section aliases are added; UI controls stay in `@flow-builder/components/component-ui`.                                                                          |
| Sanitization      | Safe HTML/text sanitization and server-safe fallbacks that avoid renderer-local DOMPurify/window branching.                                                                       | Prefer `@flow-builder/components/sdk/sanitization`; keep root exports lightweight only if definition-loader safe.                                                                                                                                     |

Theme-coupled helper APIs are allowed here only when the abstraction is a reusable SDK lifecycle/3D/rendering concern.
Theme visual redesign, token changes, or component restyling are separate work and should not be smuggled into helper migration.

### SDK versus group-local/component-local boundaries

The SDK owns helpers that are generic, author-facing, and safe to expose through public package surfaces.
That includes browser environment adapters, clipboard and timer wrappers, canvas/WebGL capability checks, reduced-motion and frame-loop helpers, generic cleanup scopes, HTML sanitization, config and data primitives, generic keyboard/ARIA interaction helpers, and reusable 3D helper entrypoints intended for component authors.
Once these helpers are migrated, generic browser, capability, rendering, sanitization, and accessibility utilities must not remain hidden in `packages/components/src/groups/viz/shared/**` just because viz components were the first consumers.

Group-local code remains the right home for shared Vue components and domain-specific behavior that is useful inside a group but not a stable public SDK primitive.
Protect examples such as `VizCanvasInteractionOverlay.vue`, viz-domain payload factories, viz-domain data transforms, and group-specific normalization layers until a later inventory proves wider reuse and an SDK API is accepted.
Component-local code remains appropriate for component-specific geometry, one-off renderer state machines, and sandbox policies such as transform deny lists that enforce isolation for a single component rather than helping authors access shared browser capabilities.

The accepted interactions split is narrow: generic helpers formerly hidden in `viz/shared/interactions.ts` such as activation-key checks, arrow navigation, stable interactive keys, and ARIA label builders belong on the SDK `interactions`/accessibility surface.
Viz event payload factories and legend payload helpers stay group-local unless future evidence proves they are reusable outside viz.

Runtime services must continue to cross package boundaries through approved SDK/facade service surfaces.
Production component code may use approved service getters where appropriate, but `configure*Service()` APIs are host, test, or package-bootstrap only and must not become component-renderer setup calls.

## Import topology and authoring rules

The root `@flow-builder/components/sdk` barrel must stay definition-loader safe: it should be lightweight, side-effect-free, and free of eager DOM, browser-global, Three.js, or heavy renderer dependencies.
Definition files, transforms, and config parsing code may import root SDK types and pure helpers without pulling renderer-only code into definition loading.

Use explicit section subpaths for helpers that depend on browser APIs, Vue renderer lifecycle, Three.js, DOMPurify/window-backed sanitization, or other runtime-heavy dependencies.
Use `@flow-builder/components/component-ui` for config-panel and UI primitives exposed by the package facade; do not import shadcn-vue or host UI bridges directly.

Preferred import topology:

```ts
import { defineComponent, numberParam } from "@flow-builder/components/sdk";
import {
  createCanvas,
  focusElementById,
  matchMedia,
  resetBrowserTimeout,
  writeClipboardText,
} from "@flow-builder/components/sdk/browser";
import { detectBrowserWebGLSupport } from "@flow-builder/components/sdk/capabilities";
import { createFrameLoop } from "@flow-builder/components/sdk/rendering";
import {
  createVizThreeScene,
  createVizOrbitController,
} from "@flow-builder/components/sdk/three-d";
import { isActivationKey } from "@flow-builder/components/sdk/interactions";
import { resolveDataPath } from "@flow-builder/components/sdk/data";
import { sanitizeHtml } from "@flow-builder/components/sdk/sanitization";
import { SchemaConfigPanel } from "@flow-builder/components/component-ui";
```

Avoid direct globals in renderers and helpers:

```ts
// Avoid: unguarded globals and eager browser assumptions.
const canvas = document.createElement("canvas");
document.getElementById("panel-heading")?.focus();
const media = window.matchMedia("(prefers-reduced-motion: reduce)");
const timer = setTimeout(resetCopyState, 1200);
```

Prefer SDK browser or rendering adapters that centralize browser checks and teardown:

```ts
const canvas = createCanvas();
const focused = focusElementById("panel-heading");
const prefersReducedMotion = matchMedia("(prefers-reduced-motion: reduce)")?.matches ?? false;
const nextCopyTimer = resetBrowserTimeout(copyResetTimer, resetCopyState, 1200);
```

`focusElementById` replaces direct `document.getElementById(...).focus()` calls with a guarded boolean result so renderers can handle missing, unsupported, or throwing focus targets without direct DOM branching.
Renderers with async internal work may dispatch `dispatchComponentReadinessEvent(element, { signal: "pending" | "ready" | "settled" | "resize-settled", surface })` from the root SDK so Agent Connect screenshot readiness can wait without package code importing host app internals; use this only from renderer/browser-context code and keep payloads bounded to ids/status, not raw data.
Accepted browser helper exports include `isBrowser`, `createCanvas`, `focusElementById`, `matchMedia`, `getDevicePixelRatio`, `requestAnimationFrame`, `cancelAnimationFrame`, `setBrowserTimeout`, `clearBrowserTimeout`, `getClipboardWriteAvailability`, `isClipboardWriteAvailable`, `writeClipboardText`, `resetBrowserTimeout`, and `cleanupBrowserTimeout` from `@flow-builder/components/sdk/browser`; `detectWebGLSupport` and `detectBrowserWebGLSupport` from `@flow-builder/components/sdk/capabilities`; `resolveReducedMotionState`, `createFrameLoop`, and `createDisposalScope` from `@flow-builder/components/sdk/rendering`; `escapeHtml`, `sanitizeHtml`, and `sanitizeHtmlToResult` from `@flow-builder/components/sdk/sanitization`; and `isActivationKey`, `getNextArrowNavigationIndex`, `createInteractiveKey`, and `createAriaLabel` from `@flow-builder/components/sdk/interactions`.
Accepted declarative transform exports include the row-transform contracts and engine from the root SDK barrel (`transform-contracts.ts`, `row-transform-engine.ts`, and `row-transform-engine-types.ts`), used by built-in transform components to share row extraction, output shaping, and chain-safe diagnostics.
Accepted Task 4 helper exports include `detectWebGLSupport`, `detectBrowserWebGLSupport`, WebGL detection types, `createVizThreeScene`, `resolveVizThreeSceneColors`, `resolveVizThreeSize`, `disposeThreeObject`, `createVizOrbitController`, `createVizPickSuppressor`, `pointerToNormalizedDeviceCoordinates`, `pickFirstThreeObject`, `createVizStaleAsyncSetupGuard`, `REDUCED_MOTION_QUERY`, `resolveReducedMotionState`, and `createFrameLoop` from `@flow-builder/components/sdk/three-d`.
These SDK helper surfaces are available for later caller migrations; documentation updates here do not imply broader caller migration work.
`@flow-builder/components/sdk/three-d` is the public subpath for Three-backed helpers; do not re-export these helpers through the root SDK barrel.
WebGL detection remains canonically implemented in `@flow-builder/components/sdk/capabilities`; the Three-d subpath exposes it as a convenience so 3D authors can find WebGL, scene, orbit, picking, stale async, motion, and frame-loop helpers in one place.
The Three-d helper barrel imports `../../data-types.ts` with an explicit `.ts` extension because package generation uses Node 22 `--experimental-strip-types`; an extensionless sibling import has failed that command in this repo.

Root-versus-subpath rules:

- Root SDK is for stable definition-loader-safe types and pure helpers such as component definitions, render props/types, config parsing, data-type parsing, and port-output shaping.
- Subpaths are required for heavy or runtime-bound helpers, especially `three-d`, DOM/browser-global adapters, renderer lifecycle loops, and sanitization backed by browser `window`.
- `@flow-builder/components/component-ui` is not an SDK helper bucket; keep it for UI/config primitives and package facade components.
- Component authors should not add new generic helper folders under individual component folders or group-local `shared/` folders when the helper is clearly cross-group and public-SDK-shaped.
- Do not keep generic browser, capability, rendering, sanitization, or keyboard/ARIA helpers hidden under `groups/viz/shared` after they are migrated to public SDK sections.
- Group-local helpers remain appropriate for domain-specific payload factories, viz-only data normalization and payload transforms, shared Vue overlay components, and behavior not yet proven reusable outside one group.
- Component-local helpers remain appropriate for component-specific geometry, component-only renderer state, and component-local sandbox policies.
- Theme-coupled helper reshaping is allowed only for reusable SDK lifecycle, motion, 3D, or rendering APIs; theme token redesign and component restyling remain out of scope.
- Runtime-service `configure*Service()` APIs are host/test/bootstrap-only; production components should use approved getters only when the runtime-service contract explicitly supports that use.
- Later enforcement should block host-app imports, non-public package internals, unguarded browser globals in shared helpers, and eager heavy dependencies from the root SDK barrel.

## Helper migration checklist

Use this checklist for one helper migration at a time so each slice stays auditable and does not accidentally expand into unrelated SDK work.

1. Select one inventoried helper candidate and confirm its target section from this document.
   Keep generic SDK helpers in public SDK surfaces, keep group-local/component-local helpers where this contract says to, and do not move unrelated helpers in the same slice.
2. Add the SDK helper implementation in the approved section surface.
   Keep root SDK exports definition-loader safe, use explicit section subpaths for browser-, renderer-, sanitization-, or Three-backed helpers, and avoid host app imports.
3. Add or update unit tests for the new helper contract before migrating broad callers.
   Cover browser guards, server-safe fallbacks, cleanup/teardown behavior, accessibility behavior, or data/config edge cases that define the helper's reusable value.
   Run the focused package test command while iterating:

   ```bash
   npm run test:components
   ```

4. Migrate the intended callers to the public SDK import surface.
   Update imports from component-local or group-local paths to `@flow-builder/components/sdk` or the appropriate section subpath, and preserve renderer/config/transform behavior without changing user-visible component semantics unless the slice explicitly includes that behavior change.
5. After import path changes, run the package standalone policy before continuing:

   ```bash
   npm run policy:standalone
   ```

6. Update docs and examples touched by the migration.
   Adjust this inventory row's migration status/rationale, update authoring examples if the preferred import path changed, and keep package docs navigation in sync only when adding, renaming, or retiring docs.
7. If the migration changes manifests, generated catalog/source-manifest inputs, or component source files that feed generated output, regenerate before validation:

   ```bash
   npm run generate
   ```

8. Once the helper migration is complete and all intended callers have moved, add or tighten lint/enforcement for the old pattern.
   Do this only after the migration is complete for that helper family; enforcement should block regressions such as new direct browser-global usage, non-public package internals, or heavy root SDK imports without stranding known unmigrated callers.
9. Run package checks before closing the slice:

   ```bash
   npm run validate
   npm run typecheck
   npm run check:standalone
   ```

10. Use the preview app commands when the helper affects renderer behavior, config panels, interaction states, or preview-runtime visibility:

    ```bash
    npm run preview:dev
    npm run preview:build
    ```

Package command references are maintained in `packages/components/docs/authoring-guide.md#supported-package-commands`.
